## Context
After `system-prompt-is-byte-stable` the system prompt held across a run, but the tool list did not: `buildWorkerToolDefinitions` took the write tools out while the agent was planning, replanning or reflecting (and for any role but executor). The tool schemas come before the history in a request, so the list changed on 35–46% of consecutive calls in the replayed daemon logs (`compaction-must-respect-the-prefix-cache`), and each change missed the whole history. Under the replay's stable-head bound the same logs cost a fifth to two fifths of the "head as logged" projection.

## Decision
- **One list.** `buildWorkerToolDefinitions` is given the task only (`PrepareIterationDeps`), so nothing it is handed names the phase or the role. It still drops control-plane tools, tools whose metadata says unavailable, and the dotnet tools without a solution.
- **One predicate.** The orchestrator's `phaseRefuses(tool, phase)` is the phase rule: a write (`isWriteOperation`) in a phase that does not write (`phaseAllowsWrites`, `src/agent-core/engine/phase-write-access.ts`); `create_skill` passes. The tool-call gate, the spine's split and the loop recovery all ask it.
- **Decided once, on the calls.** As soon as a model turn arrives the spine splits its calls (`splitCallsByPhase` → `PhaseCallSplit`): `runnable`, and a refusal for each refused call. Everything that counts calls, records steps, writes the tool sequence, emits tool events, marks a tracker or opens a gate is handed `runnable` and nothing else: the plan-review count (`PlanPhaseParams.toolCallCount`), `tool.started`/`tool.finished`, the tool turn's executor, trackers (`trackAndRecordToolResults`), control-loop marks, consensus, step records (`recordStepResultsAndCheckReflection`), the plain-loop monitor, the progress line, the trace rows and so the run's `toolTrace`. A refused call stays in the assistant turn the model made (`asMade`) and is answered there by its refusal, in the model's order, so tool_use/tool_result pairing holds. `phase-write-access.test.ts` is a tripwire: it names each line allowed to read `asMade`, `refusals` or the spine's raw `response.toolCalls`, and a new one turns it red. The spine logs "Phase write refused" (chat, phase, tools, `at: "spine"`) for each turn that had one.
- **The gate stays.** A caller that hands `executeToolCalls` a state in a phase that does not write still gets the refusal there (`at: "gate"` in the log). Nothing on the spine's path reaches it with a refused call any more.
- **The planning turn's calls run in the planning phase.** The runner moved the state to EXECUTING (the plan transition) before it ran the planning turn's calls, so the gate saw EXECUTING and a write named in that turn ran. The split is made in the turn's phase, and the tool turn is handed that phase too. Scripted models had come to rely on the hole: `file-build-flow.test.ts` and the release smoke's mock (`scripts/release/mock-kimi-hook.mjs`, its autonomy, delegation and PAOR scenarios) wrote or delegated in the planning or replanning turn, and now plan first.
- **"What can run now" asks the predicate.** The offered list answers "which tools does the run have". The one reader that runs a tool itself, the loop recovery's delegation, narrows it to the tools that run in the phase of the state it hands the gate (`delegationCandidatesIn` in `src/agents/loop-recovery-delegation.ts`, applied once at the entry of `handleBackgroundLoopRecovery`, so every choice and run of a delegate below reads the narrowed list). While reflecting that excludes the delegate tools, as the per-phase list did.
- **The turn context says it.** `buildPhaseWriteNotice` adds "## Writes in this phase" to the turn context of a planning, replanning or reflecting call: a write called now does not run, it is answered with a refusal. A reflecting turn's tool calls are not run at all (the runner reads its decision), and the notice says that too.

## Rejected alternatives
- **Recording the refusal as a failed write step** (the first version). QA measured it on 2026-11-11: refused while planning and written while executing, the verifier still asked for a targeted verification in a project with nothing to verify with (the shape `a-refused-target-closes-on-the-next-success` was written against); three refusals made every later single-write batch reflect, against one in three; a refusal turned the model's DONE into CONTINUE; and error recovery told the model to try another approach.
- **Marking the refusal result and teaching each reader to skip it** (the second to fourth versions). Each QA round found an untaught reader: the step records, the run's `toolTrace` (four refusals filled all four "Tool errors" places of the supervisor's node verifier ahead of a real failure), the plan-review gate (it counted the call list before any result existed, so with "show me your plan before you proceed" a plan plus a write skipped the review). Six filter sites, and the next reader was the next finding. The split replaced them; the readers know nothing about refusals.
- **Running the loop recovery's delegation with an executing state.** It would make the delegate run while reflecting, which never happened while the list followed the phase; a behaviour change of its own.
- **Filtering the offered list by phase for every reader of it.** The verifier's tooling check (`buildToolsAvailable`) asks what the run has: verification runs in the next executing turn, and QA read that under the per-phase list a reflection could be told "[VERIFICATION TOOLING UNAVAILABLE]" because `shell_exec` was hidden (not measured here). Only the reader that runs a tool now is narrowed.
- **Letting a planning turn's writes run once the plan is recorded** (what the runner did by accident). It saves a turn when a model plans and acts at once, but the approved task said a planning-phase write is refused, and a write that runs is a call that runs: the plan review would stay closed for that turn and the write would run before the review the user asked for. If the live count below shows the extra turn is common, this is the alternative to weigh, with the review kept closed to writes.
- **Dropping a refused call from the assistant turn** instead of answering it. The history would no longer be what the model said, and the model would not learn its write was refused.
- **Keeping the per-phase list and caching around it** (two cached heads, one per phase). A provider caches a prefix, not a set of them: the phase change still misses everything after the tools.
- **Hiding writes by description** (a "not in this phase" line in each write tool's schema). The schemas would change per phase again.
- **Running the planning turn's calls before the plan transition.** The transition can end the run (plan review, goal handoff); running the calls first would execute tools in a turn that then terminates.
- **Running a reflecting turn's tool calls so a write gets a refusal.** Reads in that turn were never run either; making reflection a tool turn is a behaviour change of its own. The notice says the calls are not run.

## Consequences
- **Readers of the offered list** (`currentToolNames` / `lastToolNames` / `availableToolNames`), which now see write tools while planning and reflecting: the loop recovery's delegation is narrowed to what runs now; the verifier's tooling check, the clarification's "can inspect locally" (it asks for a read tool) and the plan-artifact check (tool names a draft mentions) read the run's list; the end-turn handler and the context builder's runtime-artifact names ran on the executing list before and after. While planning and reflecting, a draft that names write tools outside the built-in tool-name list (a Unity or MCP write, say) now counts toward "internal tooling checklist" too.
- **Tests.** `phase-write-access.test.ts`: the split, and the tripwire over its readers. The golden runs pin the plan, act and report calls of each node to one tool list, byte for byte. `v2-agent-runner.integration.test.ts` B3 runs planning, executing, reflecting, replanning and executing through the real port on one list, and the reflecting turn's write does not run; B4 pins a planning turn's write refused and the read beside it run; B5 pins three writes refused while planning and one written while executing: three worker calls, no verification gate, a `toolTrace` of the one write, tool events for it alone. Golden run 3 (`golden-run-recovery.test.ts`) shows the node verifier the path guard's error under "Tool errors" and no refusal. `orchestrator-phase-write-gate.test.ts` sends each turn through the real tool turn, split by the real predicate: the verifier approves refused-then-written in a project with nothing to verify with, the reflection cadence after three refusals equals the one without, a refusal does not override DONE, no tracker sees one; and the other way, a write that ran and failed still waits for a verification and still overrides DONE. `tool-turn.plain-loop-monitor.test.ts` pins the control-loop tracker, the monitor, the progress line, the consensus skip, the session's answers in the model's order and that a turn in which nothing ran takes no step. `orchestrator-interactive-v2.phase3.test.ts` pins, through `handleMessage`, that an explicit plan request answered with a plan and a write parks the review, presents the plan, runs no write and makes no second call; its text-only case still parks. `orchestrator-loop-recovery-phase.test.ts` pins the loop recovery while reflecting (no delegation, no refusal as a diagnosis, journal insight, worker-trace row or progress line) and while executing (it delegates). `prepare-iteration.test.ts` pins the shell called with the task alone, and the notice.
- **What a write named while planning costs.** When nothing asks for a plan review, the round trip to write it again in the executing turn, and the tool_use and its refusal in the history. Nothing else: no step, gate, cadence change, trace row, tool event, tracker mark or progress line. When the review parks (the user asked to see the plan first, the answer reads as a plan, autonomous mode is off), the run stops at the review with the write not run.
- **The consensus review** sees the calls that run, not the refused ones, and is not consulted for a turn in which nothing ran.
- **A read named beside a plan the user asked to review still skips the review,** as before this change: a read is a call that runs. Not changed here.
- **Still changing the list mid-run:** the read-only streak intervention (one turn with progress tools only), a dotnet solution appearing, and tools registered mid-run. Each is rare next to a phase change.
- **Not measured:** a live run. `cache-hit-report.mjs` on a run after this change, the replay's head churn on its log, and the daemon log's "Phase write refused" count are the measurement.
