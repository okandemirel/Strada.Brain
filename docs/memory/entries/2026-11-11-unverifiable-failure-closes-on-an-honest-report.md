## Context
Golden run 4 (2026-11-06): a write failed at run time (the filesystem refused it), the next write succeeded, and the project had no build and no tests. The targeted-repro and unverified-failure checks kept the failure open until a verification ran. Nothing could run one: the worker was asked six times, loop detection blocked the node, the goal ran again from the start, and the re-run, with an empty failure history, completed with no verification at all. The gate added cost and protected nothing.

## Decision
`decideUnverifiableExit` (`src/agents/autonomy/verifier-pipeline-unverifiable.ts`) builds a table with one row per input: what it asks, where it is read, what was read, what an unknown does, and its effect. The table goes into `evidence.unverifiableDecision`. The exit opens only when every deciding row allows it, and a row that cannot be read keeps the gate:
- the tool names offered to this turn were passed in, and none of them `runsVerificationCheck`. The record says where the answer came from (`evidence.verificationTooling.source`);
- the offer was not narrowed: an offer of writers only (restrictToProgressTools) or a plan node whose text names a tool (selectNodeTools) counts as not measured, because both hide tools that still run;
- when shell_exec is offered, no directory of the project declares a check it could run (`measureProjectChecks` in `src/agents/autonomy/verifier-pipeline-project-checks.ts`). "None" is said only of a whole tree: every directory is read except the dependency, build-output and VCS folders in `SKIPPED_DIRS`, within `SCAN_LIMITS` (20 000 entries, 12 levels). A limit reached, an unreadable directory or a linked directory makes the scan incomplete, and an incomplete scan keeps the gate. The record states the directories read and the limits, and so does the notice. In each directory it looks for: package.json test/build/check/lint scripts other than npm init's placeholder, a known test or build tool among package.json's dependencies (typescript, vitest, jest, …), a Makefile test/build/check target, a .sln or .csproj, a tsconfig.json or conftest.py, a test file at the root (test_*.py, *_test.go, *.test.*, *.spec.*), a test/ tests/ __tests__/ spec/ directory, or a manifest whose kind always carries a check (pyproject.toml, pytest.ini, Cargo.toml, go.mod, pom.xml, a Unity ProjectSettings and others). The record lists every manifest looked for and those found (`evidence.verificationTooling.projectChecks`). An unknown or unreadable root counts as not measured;
- no check ran in the run: no verification step with a verdict, and no `verificationState.lastVerificationAt` (a check older than the 50-step window still counts);
- every open failure was answered by a later success (`failureAnsweredBy` in `src/agents/autonomy/completion-review-answers.ts`, recorded in `recentFailureAnswers`):
  - any tool, shell_exec included, is answered by the same call run again: same tool and same input (`StepResult.inputSignature`, a digest of the sorted-key input);
  - a writer that creates a file (file_write, file_create) is also answered by the same tool later writing that path (`StepResult.targetPath`), or a file of the same name in another directory when the failed path cannot exist: one of its directories is measured, at decision time, to be a file in the project root (`fileOnPath`; golden run 4: README.md is a file, so README.md/kappa.txt cannot be written). The record names that file (`blockedBy`). Two more facts must hold. The run did not make the blocking file: no successful step named it, and no successful writer that names no path (shell_exec) ran, because then the record cannot tell. And the task names no other path with that file name that no step wrote;
  - nothing else answers. Edits, deletions, renames, file_manage and the generators are answered only by the same call. A write of another file, a same-name file whose failed path could still be written, a step without a signature, a writer without a path, and a same-name write with no root or a failed stat are not answers;
- no warn/error log entry is open;
- the draft does not report that the run failed (`isTerminalFailureReport`). That report has its own exit, and this row can only keep the gate.

The draft's words never open the exit. When it opens, `unverifiedNotice` builds "Not verified: …" from the record, in the task's language (`detectSupervisorFeedbackLanguage`, as the other system notices do): each failed call with its target and error, the call that answered it and its target ("wrote" only, because only writers answer by path), for a same-name answer the file that makes the failed path impossible, and why nothing could check the result. It never says "redone". The run's answer carries it whatever the draft said. `planVerifierPipeline` records it for the run on an approve and clears it on any other verdict. `settleVisibleBoundary` in `src/agent-core/engine/reflection.ts`, which every finished run passes, takes it and puts it under the answer: rendered with it in an interactive run, and written into the recorded answer in a background run, whose final text is read back from the last visible message. One more row reads the draft, and it can only add an ask: a draft that claims a check passed (`draftClaimsCheckPassed`) contradicts the record and is asked once per run for an honest report. A negation counts only inside the claim's own clause: in "No errors, verified it works" the "No" is about the errors. If the detector misses a claim, the user still reads the notice, and the notice says that no check ran.

Pinned:
- golden run 4: no ask, the notice is under the node's answer;
- golden run 5: a check tool is registered, and block and resume still hold;
- golden run 7: a claimed check is asked once, then the notice;
- `src/agents/autonomy/verifier-pipeline-unverifiable.test.ts`: every row in both directions;
- `src/agent-core/engine/reflection.unverified-notice.test.ts`: the interactive, background and reflection boundaries.

## Rejected alternatives
- **Decide "no verification tool" from the draft** ("this project has no build and no tests"). That judges the run by its prose.
- **Ask until the draft says "not verified", then close** (versions 1-3). That made the user's text the model's job, and the vocabulary check fell open: "nothing is left unverified" and "no unverified assumptions remain" read as admissions, so drafts that claimed tests passed closed the gate (QA, 2026-11-16). The orchestrator's steer the same day named the pattern across all three QA failures: each soft signal fell open when unsure. Hence the table, unknowns that keep the gate, and a notice the system writes itself.
- **Count shell_exec as a check tool.** It is on every run's offer, so the exit would never apply.
- **Ignore shell_exec, judging by the check tools alone** (the first version of this change). The registry has dedicated check tools for .NET and Unity only, so every Node, Python or Go project read as "nothing can verify", though the pipeline counts a shell `npm test` as a verification. QA measured it on 2026-11-15: a project with a test script closed the gate and no test ran.
- **Append the notice in each of the four handler paths** that turn an approve into visible text. Two of those files are past the 1,000-line limit, the background path may rewrite the draft through synthesis, and a path missed would show "done" with no notice. Instead the one boundary every finished run passes appends it.
- **Close any failure once the registry has no check tool.** A step that failed and was never re-run has not been repaired. It still waits.
- **Count any later success of the same tool as a re-run** (the second version). QA measured it on 2026-11-16: `node main.js` crashed, a file was edited, `shell_exec ls` succeeded, and the crash read as "re-run successfully". Only a writer may be answered by a different input.
- **Read only the project root, or the root and its first level** (versions 2-7). QA measured on 2026-11-16 that a check declared one or two levels down (app/package.json, backend/pyproject.toml, src/App/App.csproj, server/go.mod, a workspaces package) opened the exit and told the user the project declares none. Adding a few more directories leaves the next one unread. The orchestrator's steer the same day: say "none" only after a whole scan, and treat its limits as unknown.
- **Trust a same-name answer whenever the blocker is a file** (version 7). #88 measured two openings: the run wrote the blocking file itself, and the task asked for the same name at two paths, one of them never written.
- **Drop the name and let the measured impossibility answer alone** (the orchestrator's steer of 2026-11-16 03:00). README.md/alpha.txt is as impossible as README.md/kappa.txt, so QA's alpha/beta case (only notes/beta.txt written) would open again; measured by mutation on 2026-11-16. Dropping the impossibility instead and keeping only the same path closes golden run 4. The two pinned cases differ only in whether the failed file's name was written, so the exact name, read from the record, stays, and it counts only together with the disk measurement.
- **Let edits and deletions answer by path.** A later edit of the same file does not show that the failed edit's change landed, and a deletion's path is its whole input, so the same path is the same call.
- **Count a file of the same name written in another directory as an answer, always** (the fifth version). QA measured it on 2026-11-16: packages/a/index.js failed and packages/b/index.js was written; a deletion of services/a/config.json failed and services/b/config.json was deleted. Both closed the gate, and a/index.js was never written. Index files, package.json and config files share names across directories. Only a failed path measured to be impossible admits the same name elsewhere.
- **Count any later write of the same writer as an answer** (the fourth version). QA measured it on 2026-11-16: the task asked for notes/alpha.txt and notes/beta.txt, the alpha write failed, beta was written, and the notice told the user alpha was "redone". Alpha was never written.
- **Count only declared scripts and manifests** (the second version). It missed what a runner finds by itself: a tsconfig.json (`tsc --noEmit`), a conftest.py or a test file (`pytest`), vitest among the devDependencies (`npx vitest run`).

## Consequences
The measurement reads the turn's offer, not the full registry. The orchestrator gives the pipeline no other list, and `orchestrator.ts` may not grow. A turn narrowed in a way not listed above would hide a check tool and wrongly open this exit. Add the narrowing to `measureVerificationTooling` when one appears.

The manifests are read, and a failed path is measured, in the orchestrator's project root (`InterventionDeps.projectPath`; for a delegated run, its workspace lease). The record names it (`projectChecks.root`). When a run's tools write into a lease cut from that root, the lease is a copy: a manifest, or a file in a failed path, that the run itself changed in its lease is not seen until the lease is published.
